Technical Specification: Records, Image Assignment & Middleware Pipeline

1. Complete Record Structures (Data Schema)

The application handles records across three primary phases:

1-Intake / Unverified Scan Stage (ScanEntity in Room SQLite)
2-AI Extraction Payload (VisionExtractionResponse / DTO)
3-Approved Production Ledger (DailyLedgerEntity in Room SQLite & CSV Export)

A. Intake Scan Entity (ScanEntity)

Stored in the local SQLite database as soon as photos are taken for a barcode, before/during AI processing:

Field Name	Type	Description
apparel_id (PK)	String	Barcode identifier (e.g., BAR-849204) or Demo ID (demo_0001).
parent_item_id	String?	Barcode of the parent garment if cloned; null for original scans.
username	String	Operator/User ID logged into the device (e.g., operator_01).
timestamp	String	Formatted creation timestamp (YYYY-MM-DD HH:MM:SS).
image_files	String	Semicolon-delimited list of absolute local image paths on disk.
status	Int	Queue state: 0 = Pending AI Vision, 1 = Extracted / In Review, 2 = Verified / Added to Ledger, 3 = Failed.
is_demo_record	Boolean	true if generated under Demo Mode; false for genuine scans.
category	String?	Extracted top-level taxonomy (e.g. clothing, shoe, accessories).
sub_category	String?	Extracted garment type (e.g. jacket, dress, t-shirt, sneakers).
gender	String	Extracted target demographic (male, female, unisex, kids).
season	String	Extracted season (spring/summer, fall/winter, all-season).
netto	String	Net weight / garment base weight (e.g., 450g).
brutto	String	Gross weight including packaging/hangtags (e.g., 520g).
brand_name	String	Detected brand/designer name (e.g. Nike, Zara, Gucci).
country_of_origin	String	Country of manufacture parsed from care tags (e.g. Made in Portugal).
size	String	Normalized size specification (e.g. L, 32W x 34L, EU 42).
color	String	Detected dominant and secondary colors (e.g. Navy Blue / White).
material	String?	Fabric composition (e.g. 100% Cotton, 80% Wool 20% Polyamide).
original_price	String	MSRP / Tag price including currency symbols (e.g. $129.00).
*_conf (12 fields)	Float	Individual confidence ratings ( to ) for each field above.
error_message	String	Network or server error description if extraction failed.
created_at	Long	Epoch millisecond timestamp for sorting.

2. How Pictures Are Assigned to the Record Structure

The application uses an Item-Centric Multi-Photo Binding Architecture:
```
[ Barcode Lock: apparel_id ]
            │
            ├── Photo 1: IMG_<apparel_id>_0.jpg (Brand / Main Tag)
            ├── Photo 2: IMG_<apparel_id>_1.jpg (Care / Composition Label)
            ├── Photo 3: IMG_<apparel_id>_2.jpg (Price / SKU Tag)
            └── Photo N: IMG_<apparel_id>_N.jpg (Overall Garment / Detail)
                        │
                        ▼
       [ ScanEntity.imageFiles = "path1;path2;path3..." ]
                        │
         ┌──────────────┴──────────────┐
         ▼                             ▼
 [ Uploaded to Server ]    [ Referenced in Review UI ]
 Multi-part image list      Interactive swipe carousel
 for Gemini Vision AI       displayed alongside fields
```


Key Rules of Image Assignment:

1-Deterministic File Naming:
When photos are captured in CaptureScreen.kt, they are written directly to the app's secure internal storage directory (context.filesDir/scans/):

2-Atomic Semicolon Delimitation:
Multiple image paths for a single item are combined into a single string:

3-Multimodal Batch Ingestion:
When transmitting to the AI server, all image files in the list are attached as separate images multipart parts. Gemini Vision evaluates all images together in a single prompt context, allowing it to correlate information across different tags (e.g., brand from Image 1, material from Image 2, and price from Image 3).

4-Cloned / Duplicate Items:
When an item is duplicated using the Parent-Child Cloning workflow, the child record inherits the exact same image_files path string from the parent, saving storage space while keeping visual references intact.

3. What the Middleware Server Is Expected to Do

The companion middleware server acts as an authenticated gateway between Android mobile devices and Google Cloud / Gemini AI.

Architecture Overview

Key Responsibilities & API Endpoints

Endpoint 1: Device Authentication Handshake
Route: POST /api/auth/login
Request Body (application/json):

```JSON

{
  "password": "device_secure_password",
  "userId": "operator_01"
}
```

Expected Middleware Response:
```JSON

{
  "success": true,
  "token": "jwt_session_token_here",
  "message": "Authenticated successfully"
}
```

Responsibility: Authenticates warehouse operators, verifies device credentials, and returns a session JWT token.

Endpoint 2: Multimodal Apparel Vision Extraction

Route: POST /api/extract/apparel
Headers: Authorization: Bearer <jwt_token>
Request Format (multipart/form-data):
apparel_id: String (e.g. BAR-849204)
username: String (e.g. operator_01)
images: File array (image/jpeg binary parts, 1 to 8 files)
Middleware Execution Flow:
Receives and buffers multipart image streams using multer.
Converts image buffers to Gemini inline base64 image parts.
Sends images to Gemini Vision with a strict system prompt instructing structured extraction.
Returns the standardized JSON payload back to the Android client.
