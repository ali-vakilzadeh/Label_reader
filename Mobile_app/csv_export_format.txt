Section 1: This is the exact RFC 4180 output specification generated by the app during the Daily Ledger Export.
19 columns. PackageCode and SetSize were the v2 additions; CareInfo is the v3 addition
(client decision 2026-09-04). Every other column is unchanged from v1.

ENCODING: UTF-8 WITH A BYTE ORDER MARK (U+FEFF, bytes EF BB BF) as the first three bytes of the
file. This is mandatory, not a preference. Without the BOM, Excel on a Windows locale opens the
file as CP1252 and every accented character is corrupted - "ALGODON" with an accent renders as
"ALGODA-tilde-quote-N". It silently damages Brand, Country, Material and SubCategory alike.
Kotlin's File.writeText() defaults to UTF-8 with NO BOM, so the BOM must be written explicitly.

LANGUAGE: every value in this file is ENGLISH, including when the operator worked entirely in
Armenian. See Section 4. This is not a limitation to be fixed later - it is what makes the file
groupable, and the dashboard renders Armenian from it.

Section 3: Sets (SetSize) — what one row means

One CSV row is one scanned article: one barcode, one packet, one photo session. A set of 2
stockings is a single article containing two garments, so it is ONE row with SetSize=2 — not
two rows, and not a row duplicated by cloning.

- SetSize is decided by the operator in the review dialog, after extraction. It is never sent
  to Gemini and never inferred from the photos: the packaging usually hides the second item,
  so a guess would be a confident wrong answer.
- Blank, absent, 0, 1 or any non-numeric value all mean 1. Importers must not fail a row on it.
- Netto and Brutto stay exactly as read from the label — the weight of the WHOLE packet,
  not per garment. The app does not divide by SetSize. A 2-pack labelled 100g exports as
  Netto=100g, SetSize=2, and 100g is the true weight of that row.
- SetSize is NOT the invoice quantity. The dashboard keeps its own Pieces column, which counts
  scanned articles (a parent plus its clones) and is not emitted by the app. A set of 2 is one
  article: Pieces=1, SetSize=2. Multiplying the two is the reader's decision, not the app's.
- All other fields describe the set as a whole. Two garments in one packet share one barcode,
  one size, one colour and one price; a packet of mixed sizes or colours is not a set and must
  be scanned as separate articles.

Section 4: Language - why this file is English

The operator may run the whole app in Armenian: Armenian labels on every AI result, Armenian
pickers for the choices they make. None of that reaches this file. Every column here carries the
canonical ENGLISH key, and that is deliberate.

What the app does:

  displays                    stores and exports here
  "Տաբատ"                     Trousers
  "Կապույտ - Մուգ"            Blue - Navy
  "Ամառ"                      Summer
  "Nike"                      Nike            (brand: English in both modes)

The Armenian the operator reads comes from two places, neither of which is a translation:

- AI RESULTS arrive with their Armenian already rendered, in the data_hy object of the
  extraction response (api_contract.md v1.4 section 8.3). Material is why: a composition
  like "80% Cotton 20% Polyester" is not a table key and cannot be looked up in one step.
- ANYTHING THE OPERATOR PICKS OR TYPES is a lookup on the device against the tables served by
  GET /api/v1/reference-tables (api_contract.md v1.4 section 4.6), which carry
  English key + Armenian label + numeric id.

The app never translates, and neither does the AI. Armenian is displayed and then discarded;
only the English key is stored and written here.

Why it matters for this file:

- One garment type is ONE string. If the app wrote Armenian, the same trousers would arrive as
  "տաբատ", "Տաբատ" and "շալվար" on different rows, and no importer, filter or invoice total
  could group them. English keys are what make SubCategory searchable.
- The dashboard joins this file back to Armenian on its own tables when it renders a screen or
  builds an Armenian customs export. It needs a stable key to join ON, which is this column.
- Brand and Country are English even in Armenian output, by client decision (2026-08-30).
- Size, OriginalPrice, Netto, Brutto and CareInfo are free text (CareInfo is a URL) and are
  never translated in either direction. Their data_hy entry is always null.

Unmatched values: when the label said something outside the 295 sub-categories (or the brand,
country or material tables), the server returns the transcription unchanged and the app exports
that verbatim - still English, still one string. The dashboard flags it UNMATCHED and routes it
to review, where a supervisor decides its canonical English and its Armenian. Nothing is
silently corrected.

Importers must therefore:

- treat every column as English, and never attempt to detect or convert a language;
- accept a Brand, SubCategory, Country or Material value that is not in any reference table;
- match against the English column of middle_ware/reference_data/*.csv, case-insensitively.

Section 5: Vocabulary source

Brand, SubCategory, Country and Material come from tables that GROW; do not hardcode them.
The authoritative copies are middle_ware/reference_data/*.csv, which the middleware also serves
to the app. Category, Gender, Season and Color are short and fixed enough to hardcode for
validation, but their Armenian labels still come from the served tables.

| Column      | Table                | Rows | Armenian available |
|-------------|----------------------|------|--------------------|
| SubCategory | sub-category.csv     | 295  | yes                |
| Brand       | brand.csv            | 839  | no, English by decision |
| Country     | country.csv          | 222  | no, English by decision |
| Material    | material.csv         | 85   | yes (per fibre - see Section 6) |
| Color       | color.csv            | 26   | yes                |
| Gender      | gender.csv           | 7    | yes                |
| Season      | season.csv           | 5    | yes                |
| Category    | (three fixed values) | 3    | yes, via the dashboard's category.csv |

A supervisor can add a row to any of these through the dashboard without an app release; the
app picks the change up from GET /api/v1/reference-tables. Rows are only ever added or given a
missing Armenian label - an English key is never renamed or deleted, because this file and every
export already made depend on it.

Section 6: Three columns whose CONTENT changed (client decisions 2026-09-04)

The app writes these columns exactly as the server sends them. Nothing here is app-side logic;
it is recorded so the values in the file are not mistaken for defects.

MATERIAL - was one fibre, is now the whole composition.

  Until v1.3 the server reduced a composition to a single reference fibre, and "100% Cotton"
  arrived as "Cotton". The client needs the complete information, so v1.4 sends all of it:

    label reads    100% ALGODON / ALGODAO / COTTON / COTON / COTONE   (five languages)
    file gets      100% Cotton

    label reads    80% ALGODON 20% POLIESTER
    file gets      80% Cotton 20% Polyester

  One language, English. Fibre names invariant, because each segment is matched onto the 85
  reference fibres separately. Percentages exactly as printed - the server never adds them up,
  divides them or normalises them, and it never divides by SetSize.

  Do not split this column, re-order it, or try to look it up as a single key. A fibre that is
  not in the reference table passes through as transcribed, like any other unmatched value.

SIZE - European value only.

  Labels routinely print one size in seven systems. The server picks the European one and
  normalises the prefix to EU, whether the label said EU or EUR:

    label reads    US 6X/7  CA 6-8A  EUR 122/128  CN 130/64  MX 6-8A  AUS 7-8  UK 6-8Y
    file gets      EU 122/128

  The value after the prefix is verbatim - 122/128 is not simplified, split or converted.
  A label with NO European reference is written as printed, with no prefix added: a garment
  labelled only XL exports as XL, and 32W x 34L exports as 32W x 34L. The rule chooses between
  competing size systems; it does not invent one.

CAREINFO - new column, from a QR code.

  Many garments carry a QR code linking to care and usage instructions. The AI decodes it from
  the photos and returns the URL. Empty when no QR code was visible.

  Expect lower confidence here than on printed fields: a misread URL looks perfectly plausible
  and cannot be checked by eye. The dashboard already has this column (care_info) and accepts
  the header CareInfo without any importer change.
